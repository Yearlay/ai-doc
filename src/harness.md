## 网上内容总结性文章

## 一、前言

大模型本身正在快速商品化。真正的技术壁垒与商业价值，越来越集中在模型之上、应用之下的中间层，也就是 AI Agent 的运行时环境，或者说 Harness。

文章认为，单独的大模型存在几类天然短板：
- 无持久记忆
- 不能直接执行真实世界动作
- 知识会过时
- 缺少稳定可控的工作环境

因此，未来竞争重点不再只是选择哪个模型，而是谁能设计出更高效、更可靠、更安全的 Harness。模型可以替换，但围绕模型构建的运行环境、治理机制与用户体验，才是长期护城河。

### 核心战场转移：从模型本身到 Harness

过去几年，AI 工程化经历了几轮范式升级：

#### 第一阶段：Prompt Engineering
重点是把问题说清楚，优化单次调用效果。

核心关注点：
- 如何准确表达需求
- 如何增加角色、场景、示例
- 如何让模型在单轮交互中给出更好结果

局限在于：它更适合一次性任务，对多步骤、有状态、需要连续执行和验证的复杂任务支持不足。

#### 第二阶段：Context Engineering
重点是让模型在有限上下文中拿到正确的信息。

核心关注点：
- 获取上下文
- 压缩上下文
- 组织上下文
- 在有限窗口内提供足够背景信息

它解决的是模型“知道什么”的问题，但还没有解决完整运行体系的组织与治理问题。

#### 第三阶段：Agent Engineering
重点是构建更可靠的 Agent 系统。

这一阶段开始关注多步骤任务执行、工具调用、任务拆解、状态流转与基本自动化闭环。

#### 第四阶段：Harness Engineering
重点是构建 Agent 的完整运行环境。

文章给出的理解是：
- 运行环境
- 工具系统
- 记忆机制
- 评估验证
- 安全边界

这些要素共同构成一个完整的 Agent 操作系统。Harness 并不是在 Agent 之外额外增加的一个概念，而是把过去零散存在的状态管理、安全校验、执行约束、反馈机制标准化、系统化，使 Agent 从演示级工具变成可用于生产的系统。

## 二、Harness 的本质：从自动化工具到智能交付大脑

### 1. 一句话定义 Harness

文章将 Harness 描述为一种围绕开发者自治与快速安全交付构建的智能软件交付平台，也可以理解为 AI 治理的方法论、AI 编程的治理操作系统，以及 AI 工程规模化的护栏系统。

它的目标不是单纯提高生成速度，而是把 AI 的创造力约束在可控、可信的工程边界内，让软件交付过程变得可控、可靠、安全、可观测。

### 2. Agent 和 Harness 的关系

文中给出一个简化公式：

Agent = Model + Harness + Tools + Context + Memory

其中：
- Model 负责推理、生成与理解
- Tools 负责操作外部世界
- Context 负责信息与视野
- Memory 负责记忆沉淀
- Harness 负责统一编排、约束、治理与反馈闭环

文中的核心判断是：
- Model 是能力来源
- Harness 是能力边界
- Agent 是模型在 Harness 约束下借助工具完成任务的整体体系

### 3. 本质：从自动化工具到交付大脑

文章将传统工具与 Harness 做了区分：
- 传统自动化工具更像脚本执行引擎，关注“怎么跑”
- Harness 更像交付控制系统，关注“交付什么、为什么这样交付、风险如何控制”

Harness 的价值在于把代码、环境、部署、成本、安全等数据联通起来，形成统一的治理视角，而不是让团队在多个工具之间来回切换。

### 4. 解决的核心问题：消除 After-Code 瓶颈

文章认为，代码写完之后才是真正复杂度开始暴露的阶段，Harness 重点解决以下问题。

#### 1. 工具链碎片化导致的交付断层

常见现象：
- 构建、部署、监控、发布控制分别由不同系统负责
- 故障排查时需要来回切换多个工具
- 一次变更的完整生命周期很难统一追踪

Harness 的解法：
- 提供统一控制平面
- 把构建、部署、验证、回滚、发布策略、成本监控纳入一个闭环
- 让单次变更从开发到上线的全流程可追溯

#### 2. 发布风险与均值回归

常见现象：
- 回滚决策依赖人工经验
- 发布风险控制缺乏标准化与可复制性

Harness 的解法：
- 持续验证部署后的关键指标
- 自动分析延迟、错误率等信号
- 在异常时自动暂停放量或触发回滚

#### 3. 云成本失控与合规审计困难

常见现象：
- 云资源浪费难以及时发现
- 合规审计依赖人工整理

Harness 的解法：
- 把部署行为与成本数据关联起来
- 将策略以代码形式固化
- 自动拦截违规变更并保留完整审计轨迹

### 5. 最终价值：从 DevOps 工具到软件交付平台

文中认为 Harness 的目标不是替代单个 CI/CD 工具，而是在现有工具之上建立统一治理层。

对不同角色的价值：
- 对开发者：获得自助式流水线和更低门槛的安全发布能力
- 对平台或运维团队：获得标准化、可审计、可观测的交付护栏
- 对企业：缩短交付周期，降低云成本，把发布从高风险活动转为可预测工程流程

文章把 Harness 比作软件交付领域的“空中交通管制系统”，不是生产飞机，也不是修建跑道，而是确保所有变更能安全、有序、高效地起降。

## 三、Harness Engineering 的核心内容

文章将其归纳为三大治理支柱。

### 1. 架构约束

核心问题：AI 不理解系统设计意图，容易生成功能上可用、但破坏架构边界的代码。

典型风险：
- 引入循环依赖
- 破坏分层原则
- 微服务之间直接访问对方数据库
- 表示层越层访问基础设施或数据层

治理方式：
- 把架构规则转换成机器可读的规范
- 用 Linter、Fitness Function 或专用检查 Agent 自动执行
- 让 AI 生成的代码必须通过这些约束才能进入下一步

文章特别强调，关键不只是把规则写进文档，而是围绕这些规则建立自动化检查能力，实现持续治理。

### 2. 反馈闭环

核心问题：AI 产出代码太快，靠人工 Code Review 很难跟上。

治理方式：
- AI 编写代码
- 自动运行测试
- 自动分析日志和监控
- 自动修复已识别问题
- 人类只在关键决策点介入

文章认为，反馈闭环不能只停留在功能测试层面，还应覆盖：
- 安全
- 可靠性
- 性能
- 可用性

举例来说，系统如果在运行时出现 CPU 或内存异常飙升，AI 不应只是发现错误，还应具备分析和调优能力，从而推动系统自愈与自优化。

文中还引入了“熵管理”的概念：随着时间推移，AI 生成的代码会出现文档过时、命名混乱、死代码堆积等问题，因此需要专门的治理机制定期扫描、重构、同步文档，形成“用 AI 治理 AI”的自净循环。

### 3. 上下文工程

核心问题：AI 缺少项目历史、业务语义和架构背景。

治理方式：
- 构建项目级长记忆
- 将关键知识沉淀到版本控制可见的文档中
- 通过结构化文档、知识图谱或规范文件让 AI 理解项目语境

文章强调：如果团队只是口头约定规范，而没有把它写进代码仓库或知识系统，AI 就很难真正遵守这些规则。因此，上下文工程是 Harness 的信息底座。

## 四、Harness Engineering 落地

文章提到，Harness Engineering 已经开始在开源社区和实践框架中落地。其核心方向是：给 Agent 提供一个安全、高效、可扩展、可审计的真实工作环境，而不只是一个对话窗口。

文中列举了几类实践方向：
- 高灵活度的通用 Agent 框架
- 模型厂商提供的官方 Agent SDK
- 与模型深度绑定的代码生成框架
- 从零构建、满足强约束场景的自定义 Harness

作者的结论是，没有唯一最好的框架，只有是否适合团队目标、场景复杂度与安全要求。

## 五、从 Prompt 到 Harness：大模型工程化的三代范式演进与实践

这一部分是文章的重点延展内容，对三代工程范式进行了系统梳理。

### 1. Prompt Engineering：工程化起点

#### 核心定义
Prompt Engineering 是通过标准化文本设计，引导大模型按预期规则、逻辑、格式输出结果的方法。

#### 发展脉络
文章总结了几个典型阶段：
- 原生探索期：以零样本、少样本提示为主，让模型学会基础任务
- 体系化成型期：形成角色定位、任务目标、规则约束、输出要求、示例参考等结构化方法
- 自动化优化期：开始引入自动提示优化、模板化与版本管理
- 多模态与场景化融合期：Prompt 设计从文本扩展到图像、音频、视频及垂直行业
- 体系化融合期：Prompt 不再是孤立文本，而是 Skill、Agent、Harness 的标准化组成单元

#### 核心价值与边界
价值：
- 成本低
- 对齐快
- 能快速改善单次输出质量

边界：
- 无法承载大量动态知识
- 无法支撑复杂多步骤流程
- 无法提供强约束、可审计和可回滚的生产保障

### 2. Context Engineering：场景化落地核心

#### 核心定义
Context Engineering 关注如何在正确时间，以正确方式，把正确的信息注入模型上下文，从而解决知识边界、幻觉、长流程留存等问题。

#### 发展脉络
文中整理了几个阶段：
- 基础填充期：把背景信息直接拼入 Prompt
- 体系化爆发期：RAG 成为核心支柱
- 精细化管理期：开始关注上下文压缩、动态窗口与分层记忆
- 行业认知确立期：Context Engineering 从 Prompt 的附属环节升级为独立范式
- 标准化融合期：上下文管理与 Harness 深度融合，进入更完整的系统治理框架

#### 典型最佳实践
文章提到的方向包括：
- 渐进式上下文披露
- 分层记忆体系
- 混合检索的 RAG 架构
- 实时上下文同步
- 基于权限的上下文控制
- 上下文压缩与降噪

#### 核心价值与边界
价值：
- 打破知识边界
- 降低幻觉
- 让模型适配企业私有知识和实时信息

边界：
- 只能解决“基于什么信息做”
- 不能独立解决多工具协同、流程约束、合规审计、回滚与运行失控问题
- 无法处理系统长期腐化与治理自净问题

### 3. Harness Engineering：生产级落地体系

#### 核心定义
Harness Engineering 是围绕 Agent 生产级落地构建的全链路运行体系，覆盖 Prompt、Context、工具调用、流程编排、安全治理、观测审计、容错回滚、系统自净等各个环节。

其关键目标不是让模型更聪明，而是让模型在真实业务环境中可控、可靠、可审计、可进化。

#### 通俗类比
文章用驾驶系统类比三者分工：
- Prompt 是导航指令
- Context 是地图、路况和规则手册
- Harness 是刹车、安全带、交通规则、监控系统和事故处理机制

#### 核心理念
文中引用的思想可归纳为：当 Agent 犯错时，不只是修复一次，而是把这类错误沉淀为新的规则、检查或机制，让同类问题以后不再重复发生。

#### 发展脉络
文中梳理的阶段包括：
- 流程编排萌芽期：开始出现链式流程与工具调用封装
- 体系化成型期：引入状态机、DAG、安全控制、可观测性、回滚机制
- 一线规模化验证期：大型团队在内部真实项目中验证可行性
- 正式命名与行业共识期：Harness Engineering 被系统命名并快速成为高频概念

#### 核心框架
文章总结的关键维度包括：
- 上下文工程：决定 Agent 在什么时机得到什么信息
- 架构约束：决定 Agent 能做什么、不能做什么
- 熵管理：决定系统能否长期稳定，不被 AI 生成内容逐步污染

#### 开发者实操建议
文中给出一条偏实践的路线：
- 先把同一任务分别用人工和 Agent 做一遍，建立对能力边界的直觉
- 将模糊需求拆成规划和执行两个阶段
- 给 Agent 明确的验证路径
- 在项目中建立 AGENTS.md 之类的结构化说明
- 每次 Agent 犯错，就把教训沉淀成规则、文档或自动化检查
- 逐步搭建文档体系、自动化验证、可观测性与多 Agent 协同能力

#### 核心价值与行业意义
文章认为，Harness Engineering 的意义在于解决大模型概率性生成与企业生产确定性要求之间的矛盾。

它带来的改变包括：
- 工程师重心从手写代码转向设计 Agent 的运行环境
- 企业研发组织会被新的协作方式重塑
- 软件工程团队的竞争力，将越来越体现为 Harness 设计能力，而不只是编码速度

### 4. 三代范式的演进逻辑

#### 演进主线
文章把三代工程范式理解为一次持续升级：
- Prompt Engineering 解决“能用”
- Context Engineering 解决“更好用”
- Harness Engineering 解决“能稳定规模化落地”

#### 底层逻辑
三者的关注点不断上移：
- Prompt 是适配模型
- Context 是赋能模型
- Harness 是驾驭模型

#### 三者关系
文章最后强调，三者并不是替代关系，而是层层递进、相互支撑：
- Prompt 是表达与指令层
- Context 是信息与知识层
- Harness 是流程、约束、反馈与治理层

缺少任何一层，系统都很难真正进入生产场景。

## 总结

这篇文章的核心结论可以概括为：

- 大模型时代的核心竞争，正在从“谁的模型更强”转向“谁更擅长构建 Harness”
- Prompt 和 Context 仍然重要，但它们更像 Harness 体系中的基础模块
- 真正决定 Agent 能否进入生产的，是围绕模型搭建的运行环境、边界约束、验证机制、记忆体系与持续治理能力
- 工程师未来的重要工作，不只是写代码，而是设计一套让 Agent 可控、高质量、长期稳定输出的软件生产系统
